# المرحلة 7 — خارطة التنفيذ (Module by Module)

كل Module أدناه **مكتمل وقابل للاختبار بمفرده** قبل الانتقال للتالي، طبقًا لطلب المستخدم. الترتيب مصمَّم بحيث كل Module يعتمد فقط على ما قبله.

| # | Module | يشمل | معيار الاكتمال (Definition of Done) |
|---|--------|------|----------------------------------------|
| 0 | **Bootstrap** | مشروع Supabase حقيقي + تطبيق كل ملفات `supabase/migrations/*.sql` بالترتيب + نشر Edge Function `create-user` + مشروع Flutter جديد (`flutter create`) بهيكل `lib/core` فارغ + `supabase_flutter` initialize + Theme/Localization أساسي (RTL + خط عربي) | `flutter run` يفتح شاشة بيضاء RTL بدون أخطاء، والاتصال بـ Supabase ناجح (اختبار `select 1`) |
| 1 | **Auth** | تسجيل دخول/خروج/تسجيل عميل جديد، قراءة `role` من الجلسة، Router بإعادة توجيه حسب الدور، إنشاء أول Admin يدويًا | تسجيل دخول admin/technician/customer يوجّه كل واحد لواجهته الصحيحة؛ محاولة دخول تكنيشيان لواجهة الأدمن تُرفض |
| 2 | **Products & Catalog (Admin CRUD + Customer browse)** | شاشات المنتجات/الأقسام للأدمن (CRUD + رفع صور Storage) + شاشة تصفح/بحث/تفاصيل للعميل (تقرأ من `products_public`) | أدمن يضيف منتجًا بصورة، يظهر فورًا في تطبيق العميل؛ العميل لا يرى `cost_price` في أي طلب شبكة (تحقق من Network tab) |
| 3 | **Cart & Orders (Customer + Admin)** | سلة محلية، Checkout → `rpc_create_order`، متابعة الطلب Realtime، شاشات إدارة الطلبات للأدمن (تأكيد/حالة/دفعة/إلغاء) | سيناريو كامل: عميل يطلب → أدمن يؤكد → المخزون ينقص فعليًا → العميل يرى تحديث الحالة بدون Refresh |
| 4 | **Maintenance Queue (Customer + Technician + Admin)** | نموذج طلب صيانة + رفع صور + GPS، شاشة قائمة الصيانة للصنايعي Realtime، فتح خرائط، تغيير الحالات، إسناد الأدمن | سيناريو الاختبار الحي من المستند الأصلي: 4 طلبات، إنهاء الأول، تحقق أن البقية تتحدث فورًا في 3 أجهزة مختلفة (Web/Android مُحاكاة) |
| 5 | **Warehouse & Technician Bag** | صرف بضاعة (`rpc_issue_stock_to_technician`)، عرض شنطة الصنايعي، استلام مشتريات (`rpc_receive_purchase`)، سجل حركات المخزون | صرف 5 قطع لمحمد → المخزن الرئيسي -5 والشنطة +5 فورًا؛ محاولة صرف كمية أكبر من المتاح تُرفض بخطأ واضح |
| 6 | **Technician Sales & Account** | بيع من الشنطة (`rpc_technician_sale`)، حساب الصنايعي، توريد (`rpc_technician_supply`)، سجل الحركات | بيع من شنطة تحتوي 5 قطع بكمية 6 → رفض فوري؛ توريد 5000 → رصيد الخزنة +5000 ومطلوب الصنايعي -5000 فورًا |
| 7 | **Cashbox & Expenses** | شاشة الخزنة (رصيد محسوب + حركات)، تسجيل مصروفات | تسجيل مصروف 500 → رصيد الخزنة ينقص 500 فورًا، ويظهر في سجل الحركات بلا إمكانية حذف |
| 8 | **Customer Accounts (Admin)** | كشف حساب كامل لكل عميل، تسجيل دفعة يدوية | عميل بمديونية 5000 → تسجيل دفعة 2000 → الرصيد المتبقي 3000 في كل الشاشات فورًا |
| 9 | **Inventory Count (جرد)** | بدء جرد، إدخال كميات فعلية، اعتماد | جرد بفارق -3 قطع بدون سبب → رفض الاعتماد؛ بإدخال سبب → قبول وتحديث الرصيد فعليًا |
| 10 | **Dashboard** | كل المؤشرات + Charts | كل رقم في الـ Dashboard يطابق مجموع الجداول/Views يدويًا (اختبار تدقيق) |
| 11 | **Reports** | 6 تقارير + فلترة تاريخ + Export PDF/Excel | تقرير أرباح فترة معينة يطابق الحساب اليدوي `Revenue - COGS - Expenses` بالضبط |
| 12 | **Notifications** | شاشة إشعارات لكل الأدوار + Badge + Realtime | حدث صيانة جديد يولّد إشعارًا فوريًا للصنايعي المسنَد بدون تحديث يدوي |
| 13 | **Users & Roles (Admin)** | إدارة المستخدمين، تغيير الأدوار، تفعيل/إيقاف، إنشاء صنايعي (Edge Function) | إنشاء صنايعي جديد من الأدمن → يستطيع الدخول فورًا بواجهته الصحيحة |
| 14 | **Audit Log (Admin)** | شاشة قراءة فقط لكل العمليات الحساسة | تعديل سعر منتج → يظهر Row في audit_logs بالقيم القديمة/الجديدة خلال ثوانٍ |
| 15 | **Hardening & Production Readiness** | مراجعة كل RLS Policies فعليًا (محاولات وصول غير مصرح بها يدويًا)، اختبار Race Condition (طلبان متزامنان لآخر قطعة عبر سكربت اختبار)، ضبط أيقونات/splash/اسم التطبيق، بناء نسخ Release (Android/iOS إن أمكن) | Checklist القسم 9 من `04-security-architecture.md` بالكامل ✅ |

## ملاحظات على الترتيب
- **Module 0-1 إلزاميان أولًا** (لا شيء يعمل بدون Auth وRouting).
- **Module 2-3 (المنتجات + الطلبات)** يُبنيان قبل الصيانة لأنهما أبسط ويؤسسان نمط "Repository → RPC → Realtime" الذي يتكرر في كل الوحدات التالية.
- **Module 4 (الصيانة)** أهم اختبار لـ Realtime بحكم متطلب "بدون Refresh يدوي" الصريح — يُفضَّل تنفيذه مبكرًا لاكتشاف أي مشكلة معمارية في التعامل مع Supabase Realtime قبل تكرار النمط بقية الوحدات.
- **Module 5-9** كلها مالية/مخزنية حساسة، تُبنى بعد التأكد أن نمط RPC + Ledger يعمل بثبات من الوحدات السابقة.
- **Module 10-14** تجميعية (تقرأ فقط مما سبق)، لذلك تأتي أخيرًا ولا تحمل مخاطرة معمارية جديدة.
- **Module 15** بوابة الإنتاج النهائية.

## معيار عام لقبول أي Module
1. لا Business Logic داخل الـ Widgets.
2. كل عملية كتابة حساسة عبر RPC فقط (تحقق فعلي: لا توجد استدعاءات `insert()/update()` مباشرة على جداول Ledger في كود الـ Repository).
3. `Loading / Empty / Error States` مغطاة في كل شاشة تعرض بيانات غير متزامنة.
4. اختبار يدوي فعلي على المتصفح/المحاكي قبل الانتقال للـ Module التالي (وليس فقط قراءة الكود).
