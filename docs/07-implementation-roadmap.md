# المرحلة 7 — خارطة التنفيذ (Module by Module)

كل Module أدناه **مكتمل وقابل للاختبار بمفرده** قبل الانتقال للتالي، طبقًا لطلب المستخدم. الترتيب مصمَّم بحيث كل Module يعتمد فقط على ما قبله.

> **الحالة الحالية (2026-08-30):** Modules 0-14 منفَّذة في الكود (`lib/features/*`) وتُجمَّع بدون أخطاء (`flutter analyze` نظيف). Module 15 (Hardening) جزئي — راجع القسم الأخير من هذا الملف لما تم وما تبقى كاختبار حي يدوي على مشروع Supabase الفعلي.

## ملاحظة Export (Module 11)

"نسخ التقرير" الحالي يضع ملخص التقرير كنص في الحافظة (Clipboard) — يعمل فورًا بدون أي حزمة إضافية، ويمكن لصقه في Excel/Word مباشرة. تصدير PDF/Excel كملف حقيقي قابل للحفظ (حزم `printing`/`excel`) لم يُضَف عمدًا في هذه الجولة لتفادي إدخال حزمة جديدة غير مُختبَرة في نهاية الجلسة؛ هذا تغيير في طبقة العرض فقط (`admin_report_detail_screen.dart`) ولا يمس منطق التقارير أو قاعدة البيانات.

## حالة Module 15 (Hardening) — ما تم وما تبقى

**تم:**
- `flutter analyze` نظيف تمامًا (صفر أخطاء/تحذيرات) على كامل الكود.
- `flutter test` يمر بنجاح.
- بناء Release لنسخة Web ينجح بدون أخطاء.
- إصلاح كل الأخطاء الحقيقية المكتشفة أثناء الاختبار الحي على مشروع Supabase الفعلي (migrations 0014-0019) — راجع تعليقات كل ملف لتفاصيل كل Bug.
- تفعيل Realtime على `orders`, `maintenance_requests`, `notifications`.

**متبقٍّ (يحتاج اختبارًا حيًّا فعليًا على جهاز/متصفح حقيقي متصل بمشروعك، وليس مجرد كود):**
- اختبار Race Condition فعليًا (طلبان متزامنان لآخر قطعة من نفس المنتج).
- محاولة وصول غير مصرَّح بها يدويًا (مثال: طلب REST مباشر بتوكن عميل لقراءة `cash_transactions` يجب أن يُرفض).
- ضبط أيقونة التطبيق واسمه النهائي (حاليًا الافتراضي من `flutter create`).
- بناء نسخة Release فعلية لأندرويد/iOS وتجربتها على جهاز حقيقي (تم اختبار Web فقط حتى الآن).

## ملاحظات على الترتيب
- **Module 0-1 إلزاميان أولًا** (لا شيء يعمل بدون Auth وRouting).
- **Module 2-3 (المنتجات + الطلبات)** يُبنيان قبل الصيانة لأنهما أبسط ويؤسسان نمط "Repository → RPC → Realtime" الذي يتكرر في كل الوحدات التالية.
- **Module 4 (الصيانة)** أهم اختبار لـ Realtime بحكم متطلب "بدون Refresh يدوي" الصريح — يُفضَّل تنفيذه مبكرًا لاكتشاف أي مشكلة معمارية في التعامل مع Supabase Realtime قبل تكرار النمط بقية الوحدات.
- **Module 5-9** كلها مالية/مخزنية حساسة، تُبنى بعد التأكد أن نمط RPC + Ledger يعمل بثبات من الوحدات السابقة.
- **Module 10-14** تجميعية (تقرأ فقط مما سبق)، لذلك تأتي أخيرًا ولا تحمل مخاطرة معمارية جديدة.
- **Module 15** بوابة الإنتاج النهائية.

## معيار عام لقبول أي Module
1. لا Business Logic داخل الـ Widgets.
2. كل عملية كتابة حساسة عبر RPC فقط (تحقق فعلي: لا توجد استدعاءات `insert()/update()` مباشرة على جداول Ledger في كود الـ Repository).
3. `Loading / Empty / Error States` مغطاة في كل شاشة تعرض بيانات غير متزامنة.
4. اختبار يدوي فعلي على المتصفح/المحاكي قبل الانتقال للـ Module التالي (وليس فقط قراءة الكود).
