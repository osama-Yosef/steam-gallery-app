# المرحلة 10: هيكل المدفوعات (بدون أي بوابة دفع فعلية)

## المشكلة اللي كانت موجودة

مفيش أي هيكل عام للمدفوعات — الدفع النقدي بيتسجل مباشرة على الطلب (`orders.paid_amount`، Phase 9). قبل ما نوصل لبوابة دفع حقيقية (Phase 11) أو InstaPay (Phase 12) أو المحفظة (Phase 13)، محتاجين هيكل موحّد يقدر يستوعبهم كلهم من غير ما نعيد بناء حاجة في كل مرة.

## ليه المرحلة دي مفيهاش أي بوابة دفع حقيقية

المواصفات صريحة: **قبل إضافة أي خدمة مدفوعة** لازم نوضّح ليه محتاجينها، وهل فيه بديل، والتكلفة المتوقعة، وهل ممكن نأجلها. اختيار بوابة دفع فعلية (Paymob / Fawry / غيرهم) قرار له تكلفة ومصاريف تشغيل حقيقية، ومحتاج معاك — مش قرار أقدر آخده لوحدي. المرحلة دي بتبني **الهيكل بس**، وتفضل فاضية لحد ما نتفق على البوابة في Phase 11.

## قاعدة البيانات (`0038_payment_architecture.sql`)

ثلاث جداول جداد:

| الجدول | الوظيفة |
|---|---|
| `payments` | صف واحد لكل محاولة دفع (طلب أو شحن محفظة لاحقًا). فيه القناة (`cash_on_delivery` / `gateway` / `instapay` / `wallet`)، المزوّد، المبلغ، الحالة، ومرجع المزوّد |
| `payment_attempts` | سجل كل محاولة (نجحت أو فشلت) — **لا يتعدل ولا يتحذف أبدًا**، زي أي سجل مالي تاني في المشروع |
| `payment_webhook_events` | كل إشعار خام من مزوّد الدفع، بمفتاح فريد (المزوّد + رقم الحدث) — لو المزوّد بعت نفس الإشعار مرتين، التاني بيترفض من هنا قبل ما يوصل لأي منطق تاني |

### مين يقدر يكتب فيهم؟

**محدش من التطبيق.** لا العميل ولا حتى الأدمن يقدر يعمل INSERT أو UPDATE مباشر على أي جدول من التلاتة. الكتابة الوحيدة المسموحة هتيجي من **Edge Function** بتستخدم `service_role` (لما تتبنى في Phase 11/12)، بالظبط زي المسار اللي المواصفات طلبته:

```
Flutter → Edge Function (service_role) → مزوّد الدفع → إشعار المزوّد
→ Edge Function (service_role) → تحقق → تحديث payments → تنفيذ الأثر المالي → إشعار العميل
```

العميل يقدر بس **يقرا** مدفوعاته هو (`payments`)، والأدمن يقرا الكل + `payment_attempts` + `payment_webhook_events` للدعم الفني.

### الحماية من التكرار (Replay)

- **`payments`:** مرجع المزوّد الواحد مايقدرش يبقى وراء أكتر من دفعة — لو المزوّد بعت "نجح الدفع" مرتين، المحاولة التانية هترفض على مستوى قاعدة البيانات.
- **`payment_webhook_events`:** نفس الفكرة على مستوى الإشعار نفسه — كل إشعار له مفتاح فريد، فإعادة الإرسال مالهاش أي أثر تاني.
- **البيانات الأصلية للإشعار** (`provider`, `event_id`, `payload`, `received_at`) **لا تتغيّر بعد التسجيل** — بس `processed_at` و`processing_error` يقدروا يتحدّثوا لما الـ Edge Function يعالج الإشعار.

## التطبيق (Flutter)

**مفيش أي واجهة جديدة في المرحلة دي.** مفيش بوابة دفع شغالة لسه، فمفيش حاجة حقيقية تتعرض للعميل. الشاشات (سجل المدفوعات، إلخ) هتتبنى في Phase 11 لما يبقى فيه بيانات حقيقية تتعرض.
