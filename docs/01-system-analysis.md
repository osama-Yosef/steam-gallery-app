# المرحلة 1 — تحليل النظام

> نظام ERP لإدارة معرض أجهزة بخار (Vape/Steam Gadgets Retail & Service ERP)
> Flutter + Supabase (PostgreSQL, Auth, Storage, Realtime, Edge Functions, RLS)

---

## 1. نطاق النظام (Scope)

النظام **ليس** متجر إلكتروني بسيط. هو نظام ERP صغير يغطي:

- المبيعات (بيع مباشر من الأدمن + بيع الصنايعية من شنطهم)
- إدارة الطلبات من تطبيق العميل
- المخزون (مخزن رئيسي + شنط فرعية للصنايعية) وحركاته
- الجرد الدوري
- الخزنة (Cashbox) القائمة على Ledger
- المصروفات
- حسابات العملاء (آجل/مديونية)
- حسابات الصنايعية (بضاعة + مبيعات + توريدات)
- الصيانة كنظام Queue حقيقي بتحديث Realtime
- التقارير المالية والتشغيلية
- الصلاحيات متعددة المستويات عبر RLS
- سجل مراجعة (Audit Log) للعمليات الحساسة

## 2. Functional Requirements (FR)

### FR-1 عملاء
- FR-1.1 تسجيل/دخول عميل (Supabase Auth: Email أو Phone OTP — انظر Assumption A1)
- FR-1.2 تصفح المنتجات والأقسام والبحث
- FR-1.3 عرض تفاصيل منتج (صور، سعر، وصف، مواصفات، توفر)
- FR-1.4 سلة شراء (إضافة/حذف/تعديل كمية)
- FR-1.5 إنشاء طلب من السلة مع Snapshot للأسعار
- FR-1.6 متابعة حالة الطلب Realtime
- FR-1.7 إنشاء طلب صيانة (بيانات + صور + Location)
- FR-1.8 متابعة رقم الدور في قائمة الصيانة Realtime
- FR-1.9 عرض كشف حساب العميل (طلباته/مدفوعاته/المتبقي عليه)
- FR-1.10 استقبال إشعارات (حالة الطلب، اقتراب الدور)

### FR-2 صنايعي (Technician)
- FR-2.1 تسجيل دخول بحساب ينشئه الأدمن فقط (لا تسجيل ذاتي)
- FR-2.2 عرض قائمة الصيانة المسندة/المتاحة مرتبة حسب الدور
- FR-2.3 عرض تفاصيل الصيانة + فتح الموقع بتطبيق خرائط خارجي
- FR-2.4 تغيير حالة الصيانة (assigned → in_progress → completed)
- FR-2.5 عرض شنطة البضاعة الخاصة به (الكميات الحالية)
- FR-2.6 تنفيذ بيع من شنطته لعميل (مع منع البيع بكمية أكبر من المتاح)
- FR-2.7 تسجيل توريد نقدي للمعرض
- FR-2.8 عرض حسابه (بضاعة + مبيعات + تحصيل + متبقي توريد)
- FR-2.9 عرض سجل حركاته بالتفصيل

### FR-3 مدير المعرض (Admin)
- FR-3.1 Dashboard بمؤشرات سريعة
- FR-3.2 إدارة المنتجات والأقسام (CRUD + صور + باركود)
- FR-3.3 إدارة المخزن الرئيسي وحركاته
- FR-3.4 صرف بضاعة من المخزن الرئيسي لشنطة صنايعي
- FR-3.5 عمل جرد (مخزن رئيسي أو شنطة صنايعي) وتسجيل الفروقات
- FR-3.6 إدارة الخزنة (عرض الرصيد المحسوب + كل الحركات)
- FR-3.7 تسجيل مصروفات بتصنيفات
- FR-3.8 إدارة العملاء وحساباتهم (كشف حساب كامل)
- FR-3.9 إدارة الطلبات (عرض/تغيير حالة/تفاصيل)
- FR-3.10 إدارة الصنايعية (إنشاء/تعديل/إيقاف/تفعيل) وحساباتهم
- FR-3.11 متابعة الصيانة (كل الطلبات، إعادة إسناد، إلغاء)
- FR-3.12 تقارير: مبيعات، أرباح، مصروفات، مخزن، صنايعية، عملاء
- FR-3.13 Export تقارير PDF/Excel
- FR-3.14 سجل عمليات (Audit Log) كامل للقراءة فقط
- FR-3.15 إدارة المستخدمين والأدوار

### FR-4 عامة (Cross-cutting)
- FR-4.1 بحث في: المنتجات، العملاء، الطلبات، الصنايعية، الصيانة، حركات المخزن، الحركات المالية
- FR-4.2 إشعارات (Push عبر FCM اختياريًا لاحقًا + In-app عبر Realtime)
- FR-4.3 دعم عربي RTL بالكامل + Dark Mode

## 3. Non-Functional Requirements (NFR)

| # | المتطلب | التفصيل |
|---|---------|---------|
| NFR-1 | الأمان | RLS إلزامي على كل جدول، لا صلاحيات تُفرض من Flutter فقط |
| NFR-2 | الاتساق المالي | كل رصيد (خزنة/عميل/صنايعي) محسوب من Ledger وليس حقل يُعدَّل يدويًا |
| NFR-3 | منع Race Conditions | استخدام `SELECT ... FOR UPDATE` أو قيود Atomic (`UPDATE ... WHERE qty >= x`) داخل RPC Functions لأي عملية تعدل مخزون/رصيد |
| NFR-4 | منع مخزون سالب | `CHECK (quantity >= 0)` + قفل صف عند الحركة |
| NFR-5 | Auditability | تسجيل كل عملية حساسة في audit_logs عبر Triggers |
| NFR-6 | الأداء | Indexes على كل FK وأعمدة البحث/الفرز الشائعة |
| NFR-7 | قابلية التوسع | فصل طبقات Flutter (Clean-ish)، عدم تكرار منطق العمل في الواجهة |
| NFR-8 | التوفر | الاعتماد الكامل على Supabase (لا Backend مخصص إضافي) |
| NFR-9 | الخصوصية | لا يوضع Service Role Key داخل Flutter تحت أي ظرف |
| NFR-10 | إمكانية المراجعة | كل تقرير مالي يجب أن يُعاد إنتاجه بنفس النتيجة من الـ Ledger في أي وقت |
| NFR-11 | Idempotency | عمليات الشبكة الحساسة (بيع، صرف بضاعة، توريد) تحمل `client_request_id` فريد لمنع التكرار عند إعادة المحاولة أوفلاين |
| NFR-12 | RTL & i18n | كل النصوص Arabic-first، الأرقام والتواريخ بصيغة مناسبة |

## 4. User Roles

| الدور | الوصف | طريقة الإنشاء |
|------|-------|----------------|
| `admin` | مدير المعرض — صلاحيات كاملة | يُنشأ يدويًا (Seed) أو بواسطة Admin آخر |
| `technician` | صنايعي/فني | ينشئه Admin فقط عبر Edge Function (لا Self-Signup) |
| `customer` | عميل | تسجيل ذاتي عبر تطبيق العميل |

**Assumption A2:** لا يوجد دور "موظف كاشير" منفصل في هذه النسخة؛ الأدمن يمثل كل صلاحيات إدارة المعرض. يمكن إضافة دور `staff` لاحقًا بنفس آلية RLS دون تعديل جوهري.

## 6. Main Workflows (نظرة سريعة — التفصيل الكامل في `03-business-logic.md`)

1. **دورة البيع من الأدمن (Order):** عميل يطلب → Admin يؤكد → تجهيز → تسليم → تحصيل → اكتمال.
2. **دورة بيع الصنايعي:** بيع من شنطته → خصم من شنطته → تسجيل sale + sale_items → تحديث حساب الصنايعي (مديونية إن كان Cash).
3. **دورة صرف بضاعة:** Admin يصرف من المخزن الرئيسي → حركة stock_movement → المخزن -X، الشنطة +X.
4. **دورة توريد الصنايعي:** صنايعي/أدمن يسجل توريد → حركة مالية في الخزنة (+) → حركة في حساب الصنايعي (تقليل المديونية).
5. **دورة الصيانة (Queue):** عميل يطلب → يدخل الـ Queue بترتيب `created_at` → Admin يسند لصنايعي (أو تلقائي بالدور) → صنايعي ينفذ → "تم التنفيذ" → إزالة من القائمة النشطة → إعادة حساب أدوار الباقين → Realtime للعميل.
6. **دورة المصروفات:** Admin يسجل مصروف → حركة مالية (-) في الخزنة.
7. **دورة الجرد:** Admin يبدأ جرد لموقع (مخزن/شنطة) → يُدخل الكميات الفعلية → النظام يحسب الفروقات → عند "اعتماد الجرد" تُنشأ حركات `inventory_adjustment` تلقائيًا وتُحدَّث الأرصدة.
8. **حساب الخزنة:** `الرصيد = SUM(cash_transactions.amount)` حيث المبلغ موجب للدخل وسالب للمصروف — دائمًا، لا استثناء.
9. **حساب الربح:** `صافي الربح = مبيعات (Revenue) - تكلفة البضاعة المباعة (COGS بسعر التكلفة وقت البيع) - المصروفات`.

## 7. Edge Cases

| الحالة | المعالجة |
|---|---|
| بيع آخر قطعة من نفس المنتج في نفس اللحظة من عميلين/صنايعيين | RPC Function تستخدم `UPDATE stock SET qty = qty - x WHERE qty >= x RETURNING *`؛ إذا لم يُرجع صفًا → فشل العملية بخطأ "الكمية غير كافية" |
| صنايعي حاول بيع كمية أكبر من شنطته | نفس آلية القفل الذري أعلاه على `technician_bag_stock` |
| تغيّر سعر البيع/التكلفة بعد عملية بيع قديمة | لا تأثير — الأسعار Snapshot في `sale_items`/`order_items` |
| إلغاء طلب بعد الدفع | إنشاء حركة `refund` في `cash_transactions` + حركة إرجاع مخزون `return_from_customer`، لا حذف للطلب الأصلي — تغيير `status = cancelled/returned` فقط |
| صنايعي حاول تعديل حالة صيانة ليست مسندة له | يُرفض على مستوى RLS، ليس فقط UI |
| اتصال إنترنت متقطع أثناء عملية بيع | استخدام `client_request_id` (UUID يُنشأ في التطبيق) + `UNIQUE` على العمود لمنع تكرار البيع عند إعادة الإرسال |
| عميل يطلب صيانة لأكثر من مرة وهو بالفعل في القائمة | يُسمح (طلبات مستقلة)، لكن يظهر تنبيه UX فقط لا يمنع الإرسال |
| Admin يحاول حذف صنايعي عليه بضاعة أو مديونية | يُمنع حذف فعلي؛ فقط `is_active = false` (Soft Delete) طالما لديه أرصدة غير صفرية |
| جرد يظهر عجز كبير غير منطقي | لا يوجد منع نظامي، لكن يُطلب سبب (reason) إلزاميًا للفروقات، ويُسجَّل في Audit Log |
| منتج بدون صور | يُعرض Placeholder، لا يمنع الحفظ |
| عميل بدون إحداثيات GPS (رفض صلاحية الموقع) | يُسمح بإدخال العنوان نصيًا فقط، `latitude/longitude` تكون NULL، وزر "فتح الموقع" يُعطَّل عند الصنايعي |
| توريد صنايعي بمبلغ أكبر من مديونيته الفعلية | **Assumption A3:** يُسمح (قد يكون دفعة مقدمة)، الرصيد يصبح سالبًا لصالح الصنايعي (يظهر كـ "رصيد له" وليس "عليه") |

## 8. Security Requirements (ملخص)

راجع `04-security-architecture.md` للتفصيل الكامل. أهم النقاط:

- Supabase Auth + JWT يحمل `role` عبر `raw_app_meta_data` (لا يُعدَّل من العميل).
- RLS مفعّل على **كل** جدول بدون استثناء، حتى الجداول المرجعية (categories, expense_categories).
- كل تعديل على مخزون/رصيد/صيانة عبر **RPC Functions موقعة `SECURITY DEFINER`** تتحقق داخليًا من الصلاحية والقفل الذري — لا `UPDATE` مباشر من العميل على جداول الأرصدة.
- `service_role key` لا يُستخدم إلا من Edge Functions (مثل إنشاء حساب صنايعي)، أبدًا من Flutter.
- Storage Buckets محمية بسياسات RLS تربط الملف بمالكه/دوره.

## 9. Assumptions (يجب مراجعتها معك)

| # | الافتراض | البديل إن رفضته |
|---|----------|------------------|
| A1 | **[مقرر]** تسجيل الدخول لكل الأدوار (عميل/صنايعي/أدمن) بـ **رقم الهاتف + كلمة مرور** (بدون OTP/SMS) — Supabase Auth Phone Provider مع تعطيل "Confirm phone" في إعدادات المشروع، بحيث `signUp({phone, password})` يعمل فوريًا بلا رسالة تحقق. `users.email` يبقى عمودًا اختياريًا غير مستخدَم في تسجيل الدخول حاليًا | — |
| A2 | لا يوجد دور "Staff/Cashier" منفصل عن Admin في v1 | أخبرني إن أردته من البداية |
| A3 | توريد الصنايعي بمبلغ زائد عن مديونيته يُسجَّل كرصيد له (لا يُرفض) | أخبرني إن أردت منع ذلك |
| A4 | "الصنايعي يسجل توريد حسب صلاحياته" → سأمنحه صلاحية تسجيل توريد لنفسه فقط، بدون تعديل/حذف | — |
| A5 | إسناد الصيانة للصنايعي يتم يدويًا من Admin (وليس تلقائيًا بالتساوي) في v1؛ الـ Queue محسوب على مستوى النظام ككل قبل الإسناد | أخبرني إن أردت توزيعًا تلقائيًا (Round-robin) |
| A6 | العملة: جنيه مصري (EGP) بدون تعدد عملات في v1 | — |
| A7 | Export PDF/Excel للتقارير يتم من داخل التطبيق (client-side generation) وليس Edge Function، لتبسيط v1 | — |
| A8 | لا يوجد نظام "خصم/كوبونات" عام في v1، فقط خصم يدوي لكل طلب/بيع | — |

> سأمضي وفق هذه الافتراضات ما لم تُعلمني بخلاف ذلك؛ يمكن تعديل أي منها لاحقًا دون كسر التصميم لأنها معزولة في جداول/أعمدة مستقلة.
